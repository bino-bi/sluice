# Changelog

All notable changes to Sluice are documented here. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) and this project adheres to [Semantic Versioning](https://semver.org/).

Entries for each release are grouped into **Added**, **Changed**, **Deprecated**, **Removed**, **Fixed**, and **Security**. Unreleased work is appended to the `[Unreleased]` section and rolls into the next tagged release.

## [Unreleased]

### Added

- **MCP over HTTP serves TLS.** The new block `mcp.tls` takes the keys of `rest.tls`: `certFile`, `keyFile`, `clientCA` and `clientAuth`. Before, the listener of `mcp.listen` could only serve plain HTTP, so a deployment needed a TLS proxy in front. `sluice serve` and `sluice mcp --transport streamable_http` both read the block.
- **MCP over HTTP has a rate limit before login.** `limits.globalRps` and `limits.perIpRps` now also count the requests to the MCP listener. REST and MCP share the buckets, so a client has one budget for both. A request over the limit gets HTTP 429 with `ERR_RATE_LIMITED`, is counted in the new metric `sluice_mcp_rate_limited_total{scope}` and writes no audit record. **Behavior change:** `limits.globalRps` is 500 by default, so MCP over HTTP is limited without a config change, and MCP requests use up the budget of REST queries.

### Changed

- **Breaking: MCP over HTTP needs `mcp.listen`.** With `mcp.transport: streamable_http` and no `mcp.listen`, Sluice listened on port 80 of every interface. `sluice serve`, `sluice mcp` and `sluice config validate` now refuse that config.
- **`sluice mcp` does not start when an `ApprovalPolicy` is loaded.** An approver decides over the REST API, and `sluice mcp` does not start it, so a held query could never be released. **Behavior change:** the command exits with status 1 and names the cause. Run `sluice serve` with `mcp.enabled` to use approvals over MCP.
- **A JWT binding maps `claims.tenantId` and `claims.allowedRegions`.** Both keys had an effect only for API keys. In JWT mode they are now claim paths, like `claims.groups`: the value at the path becomes the claim `tenantId` or `allowedRegions` of the subject, so `{{ subject.tenantId }}` works for a nested claim such as `org.tenant`. **Behavior change:** with such a mapping, a token that lacks the path has no `tenantId` claim, also when it carries a top-level claim of that name. A binding that serves JWTs and API keys with `tenantId: "acme"` now reads `acme` as a path for JWTs.
- **Breaking: fields that had no effect are refused when a manifest loads.** These fields loaded and did nothing, so an operator could rely on a control that was not there. A manifest that sets one now fails `sluice policy validate`, `sluice config validate` and the start, with a message that names what works:
  - The kind `AuditSink`. Audit sinks come from `audit.file`, `audit.syslog` and `audit.s3` in the server config.
  - `DataSource`: `schemas`, `tables` (a data source exposes all its schemas and tables, limit access with the `resources` of a `SqlAccessPolicy`), `healthCheck` (every data source gets the built-in health test every 30 seconds), `prefix` (name the files in `allowedPaths`), `readonly: false` and an `attachMode` other than `readonly` (every data source is attached read-only). `readonly: true` and `attachMode: readonly` still load.
  - `SubjectBinding`: `groupsSource`. Groups come from `claims.groups` or `apiKeys[].groups`.
  - `RelationshipPolicy`: a `backend.type` other than `openfga`, and `backend.cacheTtl`. The cache lifetime is `policies.rebac.cacheTtl` in the server config.

  `sluice datasource check` no longer prints the columns `SCHEMAS` and `TABLES`, and its JSON output no longer has `schemas` and `tables`. `sluice schema export` no longer knows the kind `AuditSink`. The Go package `pkg/apitypes` lost the `AuditSink` types and `KindAuditSink`, `DataSourceSpec.Readonly` is now a `*bool`, and `pkg/datasource` lost `Spec.Filters`. `Spec.Raw` no longer carries `readonly`, `prefix` and `attachMode`.
- **`sluice config validate --strict` checks the keys of the server config.** `--strict` looked only at policy files. A typo in the server config, such as `policies.dir`, passed and the default stayed in use. **Behavior change:** with `--strict`, an unknown key in the file given with `--config` fails with exit status 3 and is named. Without the flag, and in `sluice serve`, such a key is still ignored.
- **Breaking: the API key pepper and the audit genesis are trimmed.** Sluice used both secrets byte for byte, so a final newline of a secret file was part of the value, while every other secret was trimmed. Spaces, tabs and line ends at the end are now cut, in `sluice serve` and in `sluice apikey hash --pepper secret://...`. A pepper typed on the command line stays as typed. A pepper secret that is empty after the cut stops the start. The secrets behind `mcp.tokenRef` and `mcp.apiKeyRef` are cut the same way, before only line ends were. **Who is affected:** a deployment whose pepper secret ends with such a character. Check with `tail -c 1 <pepper file> | od -An -c`: a `\n` means affected. After the upgrade every API key of that deployment gets 401, and no setting brings the old value back. Make each `hashRef` value again with `sluice apikey hash --pepper <ref> --id <id> --material <material>`. That needs the key material, so without it the keys must be issued again. An existing audit log is not affected, because the genesis is read only for an empty audit directory. For a new log, `--anchor` is the SHA-256 of the trimmed value.
- **`admin.token` takes a secret reference.** A value that starts with `secret://` is resolved at start, like the other secrets of the server config. Any other value stays the token itself. An empty secret stops the start, because an empty token turns the check of the admin API off. **Behavior change:** a plain token that starts with `secret://`, in any case, is now read as a reference.
- **`sluice config validate` checks the policy engine.** An unknown `policies.engine`, an unknown member in `policies.composite.members` and the `opa` engine without `policies.opa.moduleDir` passed `config validate` and stopped only `sluice serve`. All three now fail `config validate` with exit status 3.
- **Breaking: `datasources.directory` is refused.** Nothing ever read this key: `DataSource` objects load from `policies.directory`. A config that sets it, or the variable `SLUICE_DATASOURCES__DIRECTORY`, no longer starts. Remove the key. Its default `./datasources.d` is gone.
- **A policy engine that cannot decide answers 503 with the new code `ERR_POLICY_UNAVAILABLE`.** When OpenFGA was down, or a Rego module returned a result Sluice cannot read, the query failed with HTTP 500 `ERR_INTERNAL`. The audit record always said `ERR_INTERNAL`, also when the client got `ERR_TIMEOUT`. **Behavior change:** such a query now gets 503 `ERR_POLICY_UNAVAILABLE` with a generic message. It is not a deny: the query is refused, and a client may try again. The cause is logged at `error` with the `query_id`. The audit record carries the code the client gets. A check that runs into `backend.timeout` still gives `ERR_TIMEOUT`. The same holds for `explain_access` and `GET /admin/subjects/explain`.
- **The `query.*` values of reject rules and conditions cover the whole statement.** Before, they described the first SELECT of a `UNION` only, did not see the `WITH`, `ORDER BY` and `LIMIT` of a set operation, and `query.joins` counted only the `JOIN` keyword. A rule such as `query.has_select_star` or `query.joins > 3` was passed with a second SELECT or a comma join. Now `has_select_star` is true when any SELECT of the `UNION` has a star, `has_where` and `is_aggregate` need every SELECT, `where_columns` and `group_by_columns` hold the columns of all of them, `has_order_by`, `has_limit` and `limit` read the clause of the whole statement, `has_cte` and `is_recursive_cte` see a `WITH` at any depth, and `joins` counts every `JOIN` keyword and every comma between `FROM` items, also in subqueries. The OPA `input.shape` values change the same way. **Behavior change:** a rule or condition on these values can give another result for a `UNION`, a comma join, and a `WITH` or join in a subquery. A `LIMIT` inside one SELECT of a `UNION` no longer sets `has_limit`. Check your suites with `sluice policy test`.
- **Breaking: `sluice policy test` needs a `schema:` block for masked tables, and `rewrittenSql` matches change.** A table with a column mask is now read through a subquery that lists its columns (see the next entry), and the runner has no live datasource. A suite that reads a masked table must list the table's columns, in table order, in its `schema:` block. An `allow` case now fails on any rewrite error, also when it asserts nothing on the rewrite; before, such a case passed. When the schema is missing, the message says to add a `schema:` block. The rewritten SQL of every filtered or masked table changed: the table inside the subquery is named `sluice_src`, and the filter and mask columns are qualified with it. So `rewrittenSql` and `rewrittenSqlContains` values change, for example `substr(email` becomes `substr(sluice_src.email`.
- **SQL column masks are applied at the table.** The `null`, `constant`, `partial`, `hash` (sha256), `regex` and `truncate` masks replaced each use of the column in the query, with a rule per SQL form. Now a masked table is read through a subquery that lists its columns from the schema cache with the masks applied, `(SELECT sluice_src.id, NULL AS email, ... FROM shop.main.customers sluice_src WHERE <row filter>) c`, and the rest of the statement only sees masked values. The forms that were refused with `ERR_MASK_UNSUPPORTED_CONTEXT` on a table with SQL masks now return masked values: the table alias as a value (`SELECT c`, `to_json(c)`, `(c).email`), a column alias list, a join alias, `#3`, `c.* LIKE ...`, dotted field access into a masked STRUCT column, two FROM items under one alias, a subquery alias that reuses the alias of an outer masked table, and an unqualified column that two tables mask. On a query without a post-query mask, `SELECT *` is no longer expanded: DuckDB expands it over the subqueries, a star over a table with only a row filter needs no schema cache entry, and `SELECT *` over a `RIGHT` or `FULL` join with `USING` or `NATURAL` is served. On a query with a post-query mask, `SELECT *` in the outermost select list is still expanded, and a star in a subquery or CTE only when its own FROM has a table with a post-query mask. Only tables are expanded: a star in the outermost select list over a subquery, a CTE or a table function is refused with `ERR_MASK_UNSUPPORTED_CONTEXT`, now with a message that says to list the columns. `ERR_MASK_UNSUPPORTED_CONTEXT` is now only returned for post-query masks: on such a query the forms above stay refused for tables with a post-query mask, a column alias list on a table and a join alias are refused over every table, also one without a mask, and duplicate FROM names, a star in an expression and `#N` stay refused. **Behavior change:**
  - A masked table needs an entry in the schema cache. Without one the query is refused with `ERR_REWRITE_FAILED`. When the schema cannot be loaded, or the catalog is not attached, the query fails with `ERR_DATASOURCE_UNAVAILABLE`. A mask rule that names only columns makes every table it matches a masked table. Write masked tables with all three parts. A reload empties the cache, and a catalog is loaded again as a whole on the next lookup that misses one of its tables (a table not cached yet, a name that does not exist, an evicted entry). Until that load a column added at the source is not read, and a column dropped at the source makes every query on the table fail with `ERR_QUERY_FAILED`. With `cache.rewrite.enabled`, a repeated query keeps the old column list for up to `cache.rewrite.ttl` after that load. Do not rely on a new column staying hidden: add its mask before you add the column.
  - On a query with a post-query mask, a name that could reach the masked column is refused with `ERR_MASK_UNSUPPORTED_CONTEXT`, whatever else it could mean. In a subquery or CTE an unqualified name that is the post-query masked column of a table in scope is refused, also when a table of the subquery has a column of that name: qualify it (`(SELECT max(t.secret) FROM t)`). A column reference whose last name is the alias of a table with a post-query mask (the table name when it has no alias) is refused, also a real column of another table such as `o.placed_at` next to `customers placed_at`: give the table another alias. DuckDB binds such a name to the outer table in a join condition that comes before the inner table, so Sluice does not guess.
  - On a query with a post-query mask, `SELECT *` in the outermost select list over a join with `USING` or `NATURAL` is refused with `ERR_UNSUPPORTED_SYNTAX`, also over an inner join: list the columns.
  - A `USING` or `NATURAL` join on a masked column compares the masked values.
  - A masked column has the type of the mask output. A `constant` mask gives a column of the value's type, so a constant `'1900-01-01'` on a date column no longer compares with a `DATE`. A `null` mask is read as `INTEGER`, so a `USING` join of a null-masked text column with a text column fails.
  - A masked column read without an alias is named like the source column, as an unmasked column is: `SELECT "EMAIL"` returns the spelling of the table definition.
  - `rowid`, and a column qualified with the table's schema or catalog (`main.customers.email`), no longer work on a masked table without a row filter. The second is refused with `ERR_UNSUPPORTED_SYNTAX`.
  - A SQL mask is built for every masked column of the table, also one the query does not read. So a broken salt reference on one column refuses every query on the table.
  - On a query with a row filter or mask, the name `sluice_src` is reserved. A statement that contains it anywhere, also inside a longer name or a string, is refused with `ERR_UNSUPPORTED_SYNTAX`.
  - The rewritten SQL lists the columns of each masked table, so the audit `rewritten_fingerprint` changes when those columns change.
- **An EC key in a JWKS is checked when the set is loaded.** Go 1.26 deprecates the raw `X` and `Y` fields of an ECDSA public key, so the key is now built with `ecdsa.ParseUncompressedPublicKey`. **Behavior change:** a JWKS with an EC key whose point is not on its curve is refused as malformed. Before, the key was loaded and every signature check with it failed.
- **A statement DuckDB refuses returns the new code `ERR_QUERY_FAILED` (HTTP 400), not `ERR_INTERNAL`.** Before, every DuckDB error at execution was `ERR_INTERNAL`: an unknown column, a cast that fails, a mask output that does not fit the expression (`CAST(email AS INTEGER)` under a constant mask, a `USING` join of a null-masked text column with a text column). Now a statement DuckDB refuses for a name it does not know or a value that does not fit gives `ERR_QUERY_FAILED` with a generic message. These are DuckDB's binder, catalog, conversion, invalid input and out of range errors. The DuckDB text is not sent to the client: it is built from the rewritten SQL and can quote values of rows a row filter hides. It is logged at `warn` with the `query_id`. A parser error and a file or network access stopped by the hardening (permission error) stay `ERR_INTERNAL`, like every other DuckDB error. The code does not say whose SQL is at fault: a row filter on a column the table does not have, or a column dropped at the source of a masked table, also gives `ERR_QUERY_FAILED` until the policy or the catalog is fixed. The log line shows which.
- **An `ERR_INTERNAL` response is logged with its cause.** The REST, MCP and admin transports log the underlying error and the `query_id` at `error` before they answer. Before, the cause was dropped and the log showed nothing for the request. The two `501` answers of the admin API for a feature that is not enabled are not logged; their message is the whole cause. The cause is not redacted: a DuckDB message can hold a piece of the rewritten SQL and values, so treat the log as sensitive. DuckDB quotes values of the statement, so a caller could write log lines of any size. The new setting `logging.maxErrorBytes` (default 4096) cuts the text of an `error` attribute in every log line after that many bytes; `0` turns the cut off. An MCP row error after a successful start now carries the `query_id`, and a failed approval decision over REST is logged.

### Removed

- **Breaking: `GET /openapi.json` is removed.** The route answered without login with a stub that named four paths and described no operation. It now gives 404. The routes are listed in the REST API reference.

### Fixed

- **The MCP list tools show the tables without a `describe_table` first.** `list_tables`, `list_accessible_tables` and `list_catalogs` read the schema cache, and a query fills it only for a filtered or masked table. So a fresh server, and every server after a reload, listed no table. The tools now read the tables of a data source on the first call. A data source that is down is left out. **Behavior change:** `list_catalogs` hides a catalog the subject can read no table of from the first call, not only after its tables were loaded.
- **The MCP metadata tools check a table as a `SELECT`.** `list_tables`, `list_accessible_tables`, `list_catalogs` and `describe_table` asked the policy engine without an action, so a clause with `resources.actions` never matched. An allow with `actions: [SELECT]` hid the table, and a deny with `actions: [SELECT]` did not. **Behavior change:** these tools now check a `SELECT` of the subject, with empty `request.*` values as before. `explain_access`, `GET /admin/subjects/explain` and `sluice policy explain` do the same for a table without SQL. A Rego module gets `input.action` `SELECT` for these checks, not an empty text.
- **`sluice audit verify --help` names exit status 4 for a line that is not JSON.** The help text said 1. The command always returned 4.
- **The README adds the `chmod` step before `docker compose up`.** The container runs as another user and could not write the audit log to `data/`.
- **A Rego module that does not compile fails the reload.** `POST /admin/reload` answered `ok` and the log showed only a warning, while the old modules stayed active next to the new YAML policies, bindings and limits. Every policy engine now compiles its part before anything is published. **Behavior change:** such a reload answers 400 `ERR_POLICY_INVALID` and changes nothing. The same holds for a `RelationshipPolicy` whose `tokenRef` cannot be resolved.
- **A changed `.rego` file triggers a reload.** With `policies.reload` on, Sluice watched only the YAML files of the policy directory. It now also watches `policies.opa.moduleDir`, so a Rego edit no longer needs `SIGHUP` or `POST /admin/reload`.
- **The policy and schema cache metrics are exported.** `sluice_policy_evaluations_total`, `sluice_policy_denials_total`, `sluice_policy_rejections_total`, `sluice_policy_eval_duration_seconds`, `sluice_schema_cache_hits_total`, `sluice_schema_cache_misses_total` and `sluice_schema_refresh_duration_seconds` were defined, but nothing registered them, so `GET /metrics` never showed them. `sluice_audit_rotate_duration_seconds` was registered and never observed. All are live now. The counter of stale schema entries is exported as `sluice_schema_stale_entries_total`. The `sluice_policy_*` metrics count the YAML engine only. `sluice_schema_refresh_duration_seconds` times each read of the tables of a catalog. `sluice_schema_cache_misses_total` counts no miss for a name that is no catalog, so a made-up name creates no series.
- **The audit record lists the policies that matched in `Audit` or `DryRun` mode.** Such a policy showed only in `sluice policy explain` and `GET /admin/subjects/explain`. The audit log said nothing, so a rollout in `DryRun` mode could not be watched. A `query` record now has `policies_shadow`, a list like `policies_applied`. An entry has `would: deny` when a deny policy or a failed ReBAC check would have denied the query, and `would: reject` when a reject rule fired. The explain output has the same `would` field. On a deny by a composite engine, the record lists only the shadow policies of the engine that denied.
- **A request refused for a full concurrency slot is audited.** When `limits.maxConcurrent` was reached, the request got 429 `ERR_RATE_LIMITED` without an audit record and without a query id. It now leaves a `query` record with `error_code: ERR_RATE_LIMITED` and the message `service saturated`, and the answer carries the query id.
- **The `query-result` audit record names the subject.** The record that holds the row count had an empty `subject` and no `origin` and `remote_ip`. It now carries those of the `query` record. A search of the audit log for a subject now also finds the `query-result` records.
- **`sluice policy test` exits with status 3 for a policy that does not compile.** The help text says 3 for a compile failure, the command returned 1, the status of an I/O error. **Behavior change:** a script that tells 1 from 3 now sees 3.
- **`sluice schema export` works.** The row filter predicate is a type that holds itself, and the schema library stopped on it. So the export without `--kind` and `--kind RowFilterPolicy` both failed with exit status 1. The predicate is now one shared definition under `$defs`. A duration such as `timeout` is exported as text or number, not as an integer that refused `10s`. Four optional fields were marked as required and are not any more: the `name` and `expression` of a reject rule, the `name` of a condition, `rateLimit.burst` and the ReBAC `backend.type`. Every manifest under `examples/` now validates against the exported schema.
- **`sluice budget show` only reads.** The command opened the budget store like the server: it created `budget.db` when the file was missing, deleted rows older than 35 days whatever `budget.retentionDays` said, and wrote counters back when it closed, next to a running server. It now opens the file read-only and, when no server has it open, leaves no lock or log file next to it. **Behavior change:** a missing `budget.db` is an error with exit status 1, no longer an empty answer. The numbers of today are those of the last write of the server.
- **The ReBAC `backend.tokenRef` is trimmed.** The token goes into the `Authorization` header as it is. With a final newline from a secret file, every request to OpenFGA failed.
- **A row filter predicate node with two forms no longer loads.** A node that set more than one of `all`, `any`, `not` and a column check loaded, and the rewrite used only the first of them. With `{all: [...], not: {...}}` the `not` part was missing from the filter. **Behavior change:** such a policy now fails to load. Put the parts into one `all` list.
- **A removed SQLite file gives `ERR_DATASOURCE_UNAVAILABLE`.** The health test of a `sqlite` source read only the catalog of DuckDB, so the source stayed healthy after its file was removed, `GET /v1/ready` stayed 200, and queries failed with HTTP 500 `ERR_INTERNAL`. The health test now checks that the file exists, so `GET /v1/ready` turns 503 with the next test, at most 30 seconds later. When a query fails in DuckDB without a known cause and the last health test of one of its data sources failed, the client gets 503 `ERR_DATASOURCE_UNAVAILABLE`. Until that test, such a query still gets `ERR_INTERNAL`. A file that is no database is still not detected.
- **A statement that only DuckDB cannot parse gets `ERR_SYNTAX`, also without a row filter, mask or limit.** The parsers of Sluice and DuckDB differ in a few forms, such as `SELECT 1 at`, `FOR UPDATE`, `INTERVAL '1 02' DAY TO HOUR` or `WHERE id = 0x1`. On a table with a filter, mask or limit, Sluice checked the statement in DuckDB first and answered `ERR_SYNTAX`. On any other table the statement ran as sent, and the parser error of DuckDB came back as HTTP 500 `ERR_INTERNAL`. It is now 400 `ERR_SYNTAX` with the message "DuckDB cannot parse the statement". A parser error on SQL that Sluice rewrote stays `ERR_INTERNAL`.
- **`subjects.ipRanges` matches.** The identifiers stored the client address with its port (`10.1.2.3:4711`), which is no IP address, so a clause with `ipRanges` never matched. They now store the IP address alone. **Behavior change:** a clause with `ipRanges` starts to match, an allow as well as a deny. `remote_ip` in the audit record no longer has a port. The policy cache key holds the address, so a cached decision is not served to the same subject from another address. A suite for `sluice policy test` sets the address with `request.remoteIp`. Behind a proxy the address is the one of the proxy.
- **`request.remote_ip`, `request.user_agent` and `request.headers` are filled.** No transport passed them on, so a CEL condition, a reject rule or a Rego module saw empty values, and a row filter template on `{{ request.* }}` failed. REST and MCP over HTTP now fill them. Header names are in lower case, and a template finds a header in any case. The headers `Authorization`, `Proxy-Authorization`, `X-Api-Key`, `X-Approval-Token` and `Cookie` are left out. Over stdio there is no request: the values stay empty, and a `{{ request.* }}` template denies the query. **Behavior change:** a condition on `request.*` that was always false or always true can now give another result. With `cache.rewrite.enabled`, the cache key now holds the address and the user agent of the request, and every header when a policy has a CEL condition or reject rule. Such a setup gets fewer cache hits.
- **A `saltRef` or `keyRef` that is not a secret reference fails when the policy loads.** A mask with `saltRef: pepper123` loaded, `sluice policy validate` accepted it, and every query on the table then failed with `ERR_INTERNAL`. **Behavior change:** such a policy no longer loads. The value must be a `secret://env/...` or `secret://file/...` reference. A missing secret behind a valid reference still fails at query time.
- **A row filter template value that the subject does not have denies the query.** A filter such as `value: "{{ subject.tenantId }}"` for a subject without that claim failed with HTTP 500 `ERR_INTERNAL`, and the audit record said `error`. **Behavior change:** the answer is now 403 `ACL_DENIED`, the audit record has decision `deny` and names the missing value in `message`. An empty `{{ subject.email }}`, `{{ subject.issuer }}` or `{{ request.user_agent }}` counts as missing: as a bound text it matched every row in `StartsWith`, `EndsWith`, `Contains` and `Matches`. In `sluice policy test`, such a case passes with `outcome: deny`, with `errorCode: ACL_DENIED` or with both.
- **A list value works in the row filter ops `In` and `NotIn`.** `values: ["{{ subject.groups }}"]` bound the whole list as one parameter, which DuckDB cannot compare with the column. Each element of a list template is now one parameter: `team IN ($1, $2)`. This also holds for a claim that is a list. With an empty list, `In` matches no row and `NotIn` matches every row. A list on another `op`, such as `Equals`, denies the query with `ACL_DENIED`.
- **The row filter ops `IsNull` and `IsNotNull` produced SQL that DuckDB rejects.** They were written as `col OPERATOR(IS) NULL`, so every query on the table failed with `ERR_INTERNAL`. They now give `col IS NULL` and `col IS NOT NULL`. The OPA row filter form uses the same code.
- **Audit recorded a failed execution as `ERR_INTERNAL` while the client got another code.** A timeout, a cancel or an unavailable data source during execution was audited as `ERR_INTERNAL`. The audit record now carries the code the client receives.
- **`EXPLAIN SELECT` did not match action-scoped clauses.** A clause with `actions: [SELECT]` never matched `EXPLAIN`, so the tables of an `EXPLAIN` were not covered by such an allow. `EXPLAIN` over a `SELECT` now counts as `SELECT`; `EXPLAIN` over any other statement is classified as that statement.
- **Audit recorded a parse error as `ERR_INTERNAL` while the client got the right code.** When a query was allowed by policy but failed to parse, the audit record stored `ERR_INTERNAL` though the client received `ERR_SYNTAX` (or `ERR_UNSUPPORTED_SYNTAX`). The audit record now carries the same code the client receives.
- **Audit recorded some rewrite refusals as `ERR_INTERNAL`.** When the rewriter refused a query with an error the query service maps to a code (for example `ERR_MASK_UNSUPPORTED_CONTEXT` for a post-query masked column in `WHERE`, or `ERR_REWRITE_FAILED`), the audit record stored `ERR_INTERNAL`. It now carries the code the client receives.
- **`sluice policy test` reported `ERR_INTERNAL` for a refused rewrite.** `errorCode` was compared with `ERR_INTERNAL` where the server returns `ERR_MASK_UNSUPPORTED_CONTEXT`, `ERR_UNSUPPORTED_SYNTAX` or `ERR_REWRITE_FAILED`, for example for a post-query masked column in `WHERE` or a masked table without a `schema:` entry. The runner now uses the same mapping as the query service. **Behavior change:** a case that expects `ERR_INTERNAL` for such a refusal now fails.
- **`sluice policy test` did not check a case that sets only `errorCode`.** The runner ran the rewrite only for an `allow` outcome without `errorCode`, or when the case asserted on the rewritten SQL or post-query masks. So a case with `errorCode` alone passed without any check. A set `errorCode` now runs the rewrite for every outcome, and the case fails when the rewrite succeeds or returns another code. **Behavior change:** a suite with a wrong `errorCode` now fails.
- **A column qualified with the schema or catalog of a filtered table failed at execution.** A filtered table without an alias is wrapped in a subquery named after the table alone, so DuckDB could not resolve `main.orders.id` or `shop.main.orders.id` and the query failed with `ERR_INTERNAL`. Such a column is now refused with `ERR_UNSUPPORTED_SYNTAX` ("qualify the columns of table "orders" with the table name or an alias, not with its schema or catalog"). Write `orders.id`, or give the table an alias.
- **A row filter on a column named like a DuckDB keyword failed at execution.** The filter column was written bare, and DuckDB reads `anti`, `asof`, `at`, `by`, `pivot`, `qualify`, `semi`, `show` and a few more words as keywords there, so the query failed with `ERR_INTERNAL`. The filter column is now qualified with the table inside the subquery (`sluice_src.qualify = $1`), and the query runs.

### Security

- **The JWT `iat` claim is checked.** The parser that verifies a token did not check `iat`, so a token issued in the future was accepted. **Behavior change:** a token whose `iat` is later than now plus `clockSkew` (default 60 seconds) gets 401. A token without `iat` is still accepted. A token whose `iat` is not a number now gets 401 too. An identity provider whose clock runs ahead by more than `clockSkew` now gets 401.
- **A `SLUICE_*` variable is read for every scalar key.** The loader read a variable only when its key had a default or was in the file. `SLUICE_ADMIN__TOKEN` alone was ignored, and the admin API then accepted every request. The same held for `mcp.listen`, `duckdb.tempDir`, `identity.apiKeyPepper` and every key under `rest.tls`, `admin.tls`, `audit.file`, `audit.syslog` and `audit.s3`. **Behavior change:** a variable that was ignored now applies. One variable of an optional block creates the block, so `SLUICE_REST__TLS__CERTFILE` without the key file now fails the start. `SLUICE_DATASOURCES__RELOAD=true` is now refused like the key in the file. No variable sets the list `approval.webhooks`.
- **A `SELECT` that writes is stopped before DuckDB.** `SELECT ... INTO` and a `SELECT` with an `INSERT`, `UPDATE`, `DELETE` or `MERGE` inside a `WITH` were classified as `SELECT`. They reached DuckDB, which refuses both forms today, and the client got `ERR_INTERNAL`. Sluice now refuses them itself: `ERR_UNSUPPORTED_SYNTAX` for `SELECT ... INTO`, `ACL_REJECTED` for a write inside a `WITH`. A clause with `actions: [SELECT]` no longer matches such a statement.
- **An approval link decides only on `POST`.** A plain `GET` of `accept_url` or `reject_url` decided the approval. A chat client that builds a link preview, a mail scanner or a browser prefetch sends such a `GET`, so a link could be accepted by the tool that showed it. Only `HEAD` and three prefetch headers were ignored. **Behavior change:** a `GET` (or `HEAD`) now returns an HTML page with one button and changes nothing. The page is the same for every id and token. The button sends a `POST` to the same URL, and only the `POST` decides. A script that sent `GET` must send `POST`. The prefetch headers are no longer read, and a `HEAD` answers 200, not 204.
- **`columnsAccessed` holds every read of the column, `predicates` read more conditions.** A `columnsAccessed` trigger of an `ApprovalPolicy` did not fire when the query read the column without its name: `SELECT *`, the table alias as a value (`SELECT p FROM people p`), a column alias list, a position (`#2`), a `NATURAL JOIN`. It did not fire for a quoted name in another case (`"SSN"`), nor for a column inside forms such as `greatest(ssn, '')`, `ARRAY[ssn]`, an aggregate `FILTER`, a window or `USING (ssn)`. A `predicates` trigger did not fire for `country IN ('de')` under `op: "="`, nor when the column was inside a function, under `NOT` or `CASE`, in `BETWEEN` or compared with a subquery. Such a query ran without approval. **Behavior change:** column names in triggers match without regard to case. A query that reads columns of a table without naming them hits every `columnsAccessed` entry of a matching `ApprovalPolicy`, also `SELECT *` on the table. A star over a subquery or CTE that names its columns is no hit. A condition that names a `predicates` column and is not a plain comparison with a literal in `WHERE`, `HAVING`, `JOIN ... ON` or `FILTER` hits the trigger, whatever its `op` and `value`. `op: "="` also matches a value in an `IN` list, and `7` also matches `7.0`. A trigger pattern matches each part of a dotted name, so a pattern for a STRUCT column also hits `profile.city`. More queries are held than before. A `predicates` trigger is still no guard for a column: it misses a condition on an alias or on a subquery column. Use `columnsAccessed` for that.
- **`SET`, `RESET` and `SHOW` are refused.** These statements name no table, so they ran for a subject with an allow policy without `resources`. A setting that DuckDB accepted stayed on a pooled connection for later requests of any subject. A changed `search_path` let a table name without catalog get around policies that name the catalog or schema. `SHOW` listed tables, and `SHOW ALL` their columns, also for tables a deny policy covers. **Behavior change:** all three now get `ERR_UNSUPPORTED_SYNTAX` and do not reach DuckDB. Under a policy that names a table the answer stays `ACL_DENIED`. Use the MCP tools `list_tables` and `describe_table` to list what a subject can read. An allow policy without `resources` still covers the catalog views of DuckDB, such as `information_schema.tables`, and a `SELECT` on them lists every table.
- **Over MCP HTTP, a tool call ran as the subject that opened the session.** The MCP SDK connects a session once, with the request that opens it, and Sluice read the subject from that connection. A client with the `Mcp-Session-Id` of another subject ran tools as that subject. The client needed a valid credential of its own, or none when `mcp.allowAnonymous` (or `--allow-anonymous`) was on. A subject whose groups or claims changed kept the old ones until the session ended. The HTTP transport is now stateless: every request connects on its own, and a tool call runs as the subject of its request. **Behavior change:** Sluice no longer checks the value of the `Mcp-Session-Id` header, and a `GET` that asks for an event stream gets 405. A `notifications/cancelled` message no longer stops a running call. A call now stops when the client closes its request. Stdio is not affected.
- **Two star forms on a table with a post-query mask relied on DuckDB to refuse the statement.** In a nested SELECT, a star that names a table of an outer SELECT (`LATERAL (SELECT c.*)`, `(SELECT c.* FROM orders)`) and a `SELECT *` without `FROM` were not checked by the rewriter. DuckDB 1.5.5 does not expand such a star over the outer table, so no value was served raw. A DuckDB release that does would return a post-query masked column raw. The rewriter now refuses both with `ERR_MASK_UNSUPPORTED_CONTEXT` before the query runs. A star over a FROM item of its own SELECT stays served. One form that ran before is refused now: `c.*` in a subquery where `c` is a STRUCT column of that subquery and also the name or alias of an outer table with a post-query mask. Give the column another name and read its fields as `(col).field`.
- **Go 1.26.9 and dependency updates for known vulnerabilities.** Go 1.25 no longer gets security fixes, and `govulncheck` reported 13 reachable advisories: HTTP/2 and HTTP/1 issues in `net/http` and `golang.org/x/net` (among them a server crash, GO-2026-6617, and memory exhaustion through trailer headers, GO-2026-6603), `mime/multipart`, `crypto/tls`, `html/template`, an endpoint URL leak in the OpenTelemetry exporter logs (GO-2026-6505) and a gRPC memory exhaustion (GO-2026-6348). The module now needs Go 1.26 and builds with the Go 1.26.9 toolchain. `golang.org/x/net` is at v0.60.0, the OpenTelemetry modules at v1.45.0 and `google.golang.org/grpc` at v1.83.2. **Behavior change:** building from source needs Go 1.26 or later.
- **A `USING` or `NATURAL` join compared the raw value of a SQL-masked column.** `USING` and `NATURAL` name the join key without a column reference, so the mask was not applied to it. With a `null` mask on `orders.total_cents`, `... JOIN generate_series(0, 100000) AS g(total_cents) USING (total_cents)` returned each raw amount as `g.total_cents`, and `JOIN (SELECT 'alice@acme.test' AS email) x USING (email)` told whether a customer has that address. The join now compares the masked values.
- **A constant mask in `ORDER BY`, `GROUP BY` or `DISTINCT ON` became a column position.** The constant took the place of the column as a literal, and DuckDB reads an integer literal that is a whole sort or group key as a select list position. With the constant `2` on `total_cents`, `ORDER BY total_cents` sorted by the second select item, also when that item had a post-query mask, whose raw values then decided the order. `GROUP BY` and `DISTINCT ON` grouped by the wrong item or failed. The key is now the masked column.
- **A stale schema cache entry served a masked column raw.** When the cache entry of a table did not list a column yet, an unqualified reference to it was not seen as masked: `SELECT email FROM customers` returned the raw value under a `partial` mask, while `SELECT c.email` was masked. A masked table now only reads the columns its cache entry lists, so such a column is not read until the catalog is loaded again.
- **A row filter column that the table does not have bound to a name in the query.** When a filter column was missing from the table (a wildcard table pattern, a column dropped at the source), DuckDB bound the predicate to a column of another FROM item: `SELECT a.id, a.username FROM (SELECT 'acme' AS tenant_id) x, shop.main.admin_users a` returned every row. The predicate is now qualified with `sluice_src`, a name the statement may not contain, so a FROM item or struct column the query names cannot take its place. Sluice still does not check that the filter column exists, so keep it in every table a filter matches.
- **A `$n` in the query read the values the policy binds, a hash salt too.** The rewriter binds row filter values and mask parameters as `$1`, `$2`, ..., and the query service never bound the `params` of a request. So `SELECT $2 AS s, name FROM customers` returned the salt of a salted `sha256` hash mask on `name` in clear text, and `SELECT $1` on a filtered table returned the filter value, such as the tenant id. With the salt, a masked column with few distinct values can be reversed offline. A statement with a `$n` parameter is now refused with `ERR_UNSUPPORTED_SYNTAX` ("query parameters ($n) are not supported") on every path, before the rewrite cache. **Behavior change:** the `params` field of `POST /v1/query` is not supported. A statement with `$n` never ran with the caller's values, because `params` was never bound.
- **Rewritten statements could mean something else in DuckDB.** When a row filter, column mask, limit or sample applies, the rewriter changes the pg_query tree, and pg_query writes it back as SQL for PostgreSQL. DuckDB ran that text, and some forms mean something else there. So a query could return other rows than its text gives in DuckDB, or fail. Known cases: `INTERVAL '30' DAY` ran as 30 seconds; `INTERVAL '3' WEEK` (also `QUARTER`, `MILLISECOND`, the plural units and the other units pg_query does not know) ran as 3 seconds with the column name `week`; the deparse dropped parentheses, so `(a OR b) IS NULL` ran as `a OR (b IS NULL)`; a bare `FLOAT` ran as `DOUBLE`, where DuckDB reads `REAL`; `**` and `//` got another precedence (`2 * 3 ** 2` gave 36, not 18); `0x1f` ran as 31, where DuckDB reads `0 AS x1f`; alias names came back in lower case, also as `to_json` and struct keys; and the snippet of a `pkg/mask` provider was neither normalized nor checked. The rewriter now writes `LIKE ... ESCAPE`, `INTERVAL 'n' <unit>` with the six units both parsers know, casts to `json` and `bit`, and a bare `FLOAT` in the form DuckDB builds for them, and gives alias names and `EXTRACT` units such as `EPOCH` the caller's spelling back. Then, before it adds any policy SQL, a separate DuckDB instance (one thread, two connections, nothing attached, and a memory limit of 1024 bytes per byte of `limits.maxSqlBytes`, at least 256 MiB) parses the caller's text and the rewritten text with `json_serialize_sql`, and the statement is refused when the two trees differ. A mask snippet gets the same check once per distinct text. A snippet that fails it fails the query with `ERR_INTERNAL`; all built-in masks pass. `sluice policy test` runs the same check. **Behavior change** on every `SELECT` a row filter, column mask, limit or sample applies to. With a `QueryRewritePolicy` limit or sample that matches every query, that is every `SELECT`:
  - A form that DuckDB reads in another way is refused with `ERR_UNSUPPORTED_SYNTAX` ("the statement would change meaning when rewritten for row filters, masks or limits; see docs/policies/row-filters.md"). The forms, and what to write instead, are listed in "SQL forms refused on filtered or masked tables" in `docs/policies/row-filters.md`: parentheses the deparse drops, as in `(a OR b) IS NULL`, `(NOT flag) IS NULL` or `(a = 1) IN (false)` (write `coalesce(a OR b) IS NULL`), `**` and `//` (`pow`, `divide`), a lambda with a comparison body (`x -> (x > 1)`), `->>` under `AND`, `OR` or `NOT` (`flag AND (j ->> 'a') = '1'`), `0x1f` (the decimal value), `INTERVAL '1' WEEK` and the other unit aliases (`INTERVAL '1 week'`, `to_weeks(1)`), `EXTRACT` with a plural unit (the singular unit), `ARRAY[[1, 2]]` (`ARRAY[ARRAY[1, 2]]`), and a quoted name that only DuckDB reads as a keyword (`WITH "at" AS ...`, rename it).
  - A statement DuckDB cannot parse is refused with `ERR_SYNTAX` ("DuckDB cannot parse the statement"): interval ranges and precisions (`INTERVAL '1' DAY TO HOUR`, `INTERVAL '3' SECOND(3)`), `U&'...'`, `E'\u0041'`, and `0x1f + 1`. These ran before in the form pg_query wrote.
  - `LIKE ... ESCAPE` and casts to `json` or `bit` now run (DuckDB refused the deparsed form), `INTERVAL '30' DAY` is 30 days, a bare `FLOAT` is `REAL` as in DuckDB, and an alias keeps the caller's letter case in result column names and struct keys, as on pass-through. When one name appears in two spellings, as in `struct_pack(MyKey := id)` next to `AS mykey`, both stay lower case. The same happens when a keyword or type name in the statement is the same word, as in `EXTRACT(MONTH FROM d) AS Month` or `ts::date AS Date`; quote such an alias (`AS "Month"`).
  - When the check itself fails, the query fails with `ERR_INTERNAL`. A statement too large for the check (DuckDB runs out of memory) gets `ERR_PAYLOAD_TOO_LARGE`. A request canceled or timed out during the check gets `ERR_CANCELED` or `ERR_TIMEOUT`.
- **The `alias.` prefix read a post-query masked column raw.** DuckDB reads `alias.x` as the select alias `x` of the same `SELECT`, in every clause and in nested SELECTs. With a `fake` mask on `name`, `SELECT name AS n, alias.n AS m FROM customers` returned the raw names in `m`, and `WHERE alias.n = 'Alice'` and `ORDER BY alias.n` worked on the raw value. A FROM item called `alias` did not prevent it. On a query with a post-query mask, a column reference that starts with `alias.` is now refused with `ERR_MASK_UNSUPPORTED_CONTEXT`. So is a table called `alias`, by its name or its alias: `SELECT *` and `alias.*` over it are expanded to `alias.<column>`, and when the schema cache still listed a column the source no longer has, DuckDB read that as the select alias of that name. So is every column reference whose qualifier is not a table name or alias of a FROM clause in scope, because Sluice does not know what DuckDB makes of such a qualifier. A SQL mask was not affected: `alias.x` reads the masked value there. **Behavior change** on a query with a post-query mask: a column qualified with a schema or catalog (`main.customers.id`, `ERR_UNSUPPORTED_SYNTAX` before) and a STRUCT field behind a bare column name (`address.city`) are refused with `ERR_MASK_UNSUPPORTED_CONTEXT`. Qualify columns with the table name or an alias, and write `(address).city`. A column alias list on a table (`orders AS o(a, b)`) and a join alias are refused over every table, also one without a mask. A reference to a CTE counts as a table here (`q AS x(a, b)`): name the columns in the definition instead (`WITH q(a, b) AS (...)`). There the outermost `SELECT *` came back in table order under the other names, so `ORDER BY 1` sorted by another column, or the query failed with `ERR_INTERNAL`.
- **A post-query mask could be read raw in SQL.** Post-query masks (`fpe`, `fake`, `jitter`, `hash` with `hmac_sha256`) are applied in Go by result column position, so DuckDB still sees the raw value. A query could read it there: through the select alias of the masked item (`SELECT ssn AS x, x AS leak`, `WHERE x = ...`, `ORDER BY x`, `GROUP BY x`, `(SELECT x)`), through its position (`ORDER BY 2`, `GROUP BY 1`, also inside `ROLLUP`, `CUBE` and `GROUPING SETS`, and `DISTINCT ON (2)`), through `SELECT DISTINCT`, through a `USING` or `NATURAL` join, and through the condition of a join nested in another join. `unnest` of a struct in the select list added result columns, so the mask was applied to the wrong column and the masked column was served raw. All these forms are now refused with `ERR_MASK_UNSUPPORTED_CONTEXT`. The query service also checks the result before it serves a row: when the column count, or the column name at a masked position, is not what the rewriter planned, the query is refused with the same code. The default message of `ERR_MASK_UNSUPPORTED_CONTEXT` now reads "a post-query masked column is used outside a bare select item". **Behavior change:** when a select item carries a post-query mask, its alias cannot be used anywhere else in the statement (the bodies of its own `WITH` clause excepted), its position cannot be used in `ORDER BY`, `GROUP BY` or `DISTINCT ON`, and `SELECT DISTINCT` and `unnest` in the select list are refused. A `USING` or `NATURAL` join is refused when a side is a table with a post-query mask. Positions of other items still work.
- **A post-query masked column named like a SQL value keyword was served raw.** pg_query parses a bare `CURRENT_DATE`, `CURRENT_TIME`, `CURRENT_TIMESTAMP`, `LOCALTIME` or `LOCALTIMESTAMP` as a function, so the post-query mask checks did not see a column there. DuckDB binds the word to a column, a select alias or a table of that name first. With a `fake` mask on a column `current_date`, `SELECT id, current_date AS d FROM kw` returned the raw values, and `WHERE CAST(current_date AS VARCHAR) LIKE ...` and `ORDER BY current_date` worked on them. The same held for the select alias of a masked item (`SELECT name AS localtime, localtime AS leak`) and for the alias of a table with a post-query mask (`SELECT current_date FROM customers "current_date"` returned the whole row). The bare word is now checked like an unqualified column of that name and refused with `ERR_MASK_UNSUPPORTED_CONTEXT` in these cases. The quoted name (`"current_date"`) was masked before and still is. A SQL mask was not affected.
- **`EXPLAIN` showed mask salts and data behind the row filter.** On a table with a row filter or column mask, `EXPLAIN` printed the rewritten plan: the mask expression with its bound salt (`sha256(concat('<salt>', email))`), the filter with the tenant value, and row estimates; `EXPLAIN ANALYZE` also printed row counts. `EXPLAIN` in any form, `ANALYZE` included, is now refused with `ERR_UNSUPPORTED_SYNTAX` when the decision has a row filter or column mask. **Behavior change:** `EXPLAIN` only works on tables without row filter and mask. An `EXPLAIN` is still served when only a `QueryRewritePolicy` limit matches, and the limit is not applied to it.
- **Identifiers longer than 63 bytes skipped table policies.** pg_query cuts an identifier at 63 bytes, DuckDB does not. Policy matched the cut name, so a deny or row filter on a longer table name did not apply and the statement was served unchanged. A CTE named with the first 63 bytes of a table name also hid that table from policy. Any identifier longer than 63 bytes (a quoted name counts after decoding, the content of a `U&"..."` name as written) is now refused at parse time with `ERR_UNSUPPORTED_SYNTAX` ("identifier longer than 63 bytes, use a shorter name or rename the object at the source"). A deny that matches the full name still wins. **Behavior change:** tables and columns with longer names cannot be queried through Sluice. Expose them under a shorter name at the source, and keep aliases and CTE names at 63 bytes or less.
- **A filtered table named like a DuckDB keyword changed the join and lost its mask.** A filtered table without an alias gets a wrapper subquery named after the table, and pg_query writes a lower-case name bare. For a qualified name such as `main."semi"`, DuckDB read the name as a keyword. `semi`, `anti`, `asof` and `positional` turned the join into another join type and dropped the wrapper's name, so DuckDB returned other rows than written, and a masked column read as `unnamed_subquery.<column>` came back raw. Other keywords (`at`, `by`, `qualify`, `pivot`, `show` and more) broke the statement. Such a table is now refused with `ERR_UNSUPPORTED_SYNTAX` ("give table "semi" an alias"). A test checks the list against `duckdb_keywords()`. **Behavior change:** a filtered table with such a name needs an alias.
- **A FROM alias `qualify(x)` read a masked column raw.** pg_query reads `generate_series(1, 1) AS qualify(x)` as an alias with a column list and writes it bare as `qualify(x)`. DuckDB read that as `QUALIFY (x)`, a row predicate on the raw value of any column `x` in scope. `... FROM staff s, generate_series(1, 1) AS qualify(is_admin)` returned only the rows where the masked `is_admin` was true, and the select alias of an item with a post-query mask could be read the same way. The parser now refuses with `ERR_SYNTAX` every FROM alias that DuckDB reads as a keyword when written bare: `semi`, `anti`, `asof`, `positional`, `qualify`, `by`, `pivot`, `show` and the other words of the wrapper list above. **Behavior change:** these words cannot be used as a table, subquery or function alias.
- **Quoted names in another letter case skipped row filters and masks.** DuckDB resolves catalog, schema, table, alias and column names without regard to case, also when quoted. Sluice compared them exactly, so `SELECT "EMAIL" FROM customers` returned the masked column raw, and a table written as `"CUSTOMERS"` was matched by no table-scoped policy. Names are now folded to lower case in the table walker, in policy selectors and in the rewriter. **Behavior change:** table names in the audit log, in `query.tables`, in the OPA input (`input.tables`) and in the ReBAC `{{catalog}}`, `{{schema}}` and `{{table}}` placeholders are lower case.
- **`EXPLAIN` over a statement that is not a `SELECT` was accepted.** `EXPLAIN ANALYZE` runs its body. `EXPLAIN ANALYZE CREATE TABLE ... AS SELECT ...`, `INSERT`, `UPDATE` and `DELETE` passed the read-only gate, and the `SELECT` inside got no row filter and no mask. `EXPLAIN` is now classified by its body.
- **A two-part table name skipped row filters and masks.** DuckDB reads `shop.customers` as catalog `shop` with its default schema. The table walker and every policy read it as schema and table, so no filter or mask written for `shop.main.customers` matched. The query service now refuses a two-part name whose first part is an attached catalog with `ACL_REJECTED`. Write `catalog.schema.table`.
- **A table alias that is a DuckDB join keyword skipped the row filter and mask.** pg_query reads `semi`, `anti`, `asof` and `positional` as ordinary table aliases and deparses them bare, but DuckDB reads them as a join-type prefix. `SELECT ... FROM customers "semi" JOIN orders ...` therefore ran as a `SEMI JOIN` in DuckDB: the row-filter wrapper lost its alias (DuckDB named it `unnamed_subquery`) and the mask substitution the rewriter keyed on the alias did not apply, so the raw column came back. A FROM alias that is one of those four keywords, or another keyword DuckDB reads in a bare alias (see the `qualify(x)` entry above), is now refused with `ERR_SYNTAX`; use another alias.
- **An allow policy admitted the whole statement, so a joined table with no allow leaked.** An `SqlAccessPolicy` with `effect: allow` matched the request as soon as any one referenced table matched it, so a query that joined an allowed table with an unprotected one (or hid it in a `VALUES` subquery), or that read a system view such as `duckdb_databases` as a plain table, returned that table's rows unless an explicit `deny` covered it. The access gate now requires every referenced table to be covered by some allow; an uncovered table is denied with `no SqlAccessPolicy allows <table>`. Different tables may be covered by different allow policies, and a deny still overrides. Like the no-allow case the deny is an abstain, so in a `composite` engine an OPA member, which decides on the whole table list, can still allow the statement. **Behavior change:** a query that references a table no allow names is denied (`ACL_DENIED`) instead of being admitted by an allow on another table in the same statement. List every table a workload joins.
- **An access policy's `exclude` switched it off for the whole statement.** If any referenced table matched a `SqlAccessPolicy` `exclude`, the whole policy was dropped. A deny on `finance` with a carve-out for `finance.public_rates` therefore stopped denying `finance.payroll` once the query joined `public_rates`, and an allow with a carve-out stopped covering any table. `exclude` now carves out tables one by one: the policy is dropped only when it excludes every referenced table (a subject carve-out does), an allow still covers its other tables, and a deny still fires if its selector matches the tables that are left.
- **A ReBAC member granted access on its own.** In a `composite` engine with `[yaml, rebac]` the documented contract is that a query needs its `SqlAccessPolicy` allow and every matching relationship check must pass. A passing check returned an allow, so a query on a table no `SqlAccessPolicy` names, or a join of such a table with a related one, was admitted. Passing checks now record the policy and abstain; a failing check still denies. A RelationshipPolicy scoped by `resources.actions` never matched because the engine did not pass the statement's action, so its checks never ran; it now runs. **Behavior change:** a composite that relied on ReBAC alone to admit a table now needs an allow from the YAML or OPA member.
- **A CTE named after a table hid the table from policy.** The table walker treated every name of a `WITH` clause as a CTE inside all the CTE bodies. DuckDB binds a non-recursive CTE's own name, and any name of a later sibling, to the real relation, so `WITH duckdb_databases AS (SELECT * FROM duckdb_databases) SELECT ...` read the system view while policy saw no table. A CTE name is now in scope only in the siblings after it and in the statement body, and for `WITH RECURSIVE` over a `UNION` also in that union's right arm, which is where DuckDB binds it.
- **A selector that named only tags matched every table.** A `resources` block with `tags` and no catalog, schema or table pattern skipped the tag check, so an allow by tag covered untagged tables and a deny by tag blocked every query. Tag-only selectors now match only the tagged tables. A classification rule that names only columns still matches every table (a mask by its tag wants that), so an `effect: allow` by such a tag is now a compile error.
- **A dotted catalog, schema or table pattern silently matched nothing.** Each of these fields is compared with one name segment, so `tables: ["shop.main.customers"]` never matched and a row filter or mask written that way was not applied. The README quick start and most row-filter, column-mask, approval and classification examples used this form. Loading such a pattern is now an error, `sluice config validate` reports it (it now runs the policy compiler like `sluice policy validate`), and the examples use separate `catalogs`, `schemas` and `tables` fields. **Behavior change:** a policy directory with a dotted pattern fails to load; write `catalogs: ["shop"], schemas: ["main"], tables: ["customers"]`. A name that really contains a dot is written with an escaped dot (`sales\.2024`).
- **Row filters were skipped in expression subqueries.** A row filter was only injected for tables in a FROM clause, a CTE body or a set-operation arm. A table read by a subquery in the select list, `WHERE`, `HAVING`, `JOIN ... ON`, `ORDER BY`, `LIMIT` or a `VALUES` row was read unfiltered, so `SELECT (SELECT count(*) FROM t)` counted the rows of every tenant. The filter is now injected in every `SELECT` of the statement.
- **Column masks could be bypassed by reaching a column under another name.** `SELECT *` inside a FROM subquery or an expression subquery was not expanded, so `SELECT q.email FROM (SELECT * FROM customers) q` returned the raw column when a row filter was active. A `VALUES` row, the table alias used as a value (`SELECT c FROM customers c`, `to_json(c)`), a column alias list (`customers AS c(a, b)`) and a join alias (`(a JOIN b ON ...) AS j`) also returned masked columns raw. Stars are now expanded in every `SELECT`, `VALUES` rows are masked, and the three alias forms are refused with `ERR_MASK_UNSUPPORTED_CONTEXT` when the table has a mask. The same code is returned for the schema-qualified table used as a value (`main.customers`), two FROM items under one alias, a positional reference (`#3`), dotted field access into a masked STRUCT column, and an unqualified column that two tables of one FROM clause both mask. All of these were served raw before. A post-query masked column is now refused everywhere except as a bare item of the outermost select list: inside `ARRAY[...]`, `COLLATE` or a subscript, in `ORDER BY` and `DISTINCT ON`, and inside a subquery or CTE. A mask on the column a row filter tests no longer rewrites the filter predicate. On a query with masks, `c.*` inside an expression and a subquery alias that reuses the alias of an outer masked table for another table are refused. On a query with a post-query mask, `EXISTS (SELECT * ...)` is rewritten to `EXISTS (SELECT 1 ...)` when the star is the whole select list and the subquery has no `ORDER BY`, `GROUP BY` or `DISTINCT ON`. **Behavior change:** `SELECT *` over a filtered or masked table inside a subquery now needs the schema cache like a top-level star does. `SELECT *` over several tables returns the columns in FROM order (the order was random before), keeps the columns of subqueries and functions in FROM (they were dropped before), and `q.*` over a subquery alias works. A star over a `RIGHT` or `FULL` join with `USING` or `NATURAL` on a filtered or masked table is refused with `ERR_UNSUPPORTED_SYNTAX`, list the columns instead.
- **A deeply nested statement crashed the server.** pg_query parses and deparses in C with a recursive descent, and a statement nested past a few thousand levels (a long `a+a+a+...` chain, chained casts or `||`, thousands of `JOIN`s or `UNION`s, deeply nested subqueries or `CASE`) overflowed the C stack and killed the process. A C stack fault cannot be recovered in Go, so one authenticated request took the server down. The parser now measures nesting from the token stream before handing the statement to pg_query and refuses anything past a conservative depth with `ERR_UNSUPPORTED_SYNTAX` ("statement nesting is too deep"). Flat constructs do not nest and are not limited: a long `IN` list, an `AND`/`OR` chain, a wide select list and `VALUES` with many rows still parse (subject to `limits.maxSqlBytes`).
- **Policy bypass through DuckDB functions.** Policies are keyed on table references, and a function in `FROM` is not one. A query that referenced one allowed table could read any attached table through `query_table(...)`, `query(...)` or `sqlite_scan(...)` without row filter and mask, and could read host paths and settings through `duckdb_databases()`, `duckdb_settings()` and `current_setting(...)`. `COLUMNS('col')` returned masked columns unmasked, and `TABLESAMPLE` skipped row filter and mask. The audit log recorded these requests as a normal allow. Function calls are now default-deny: in `FROM` only `generate_series`, `range` and `unnest` without column references or subqueries in their arguments, outside `FROM` only a reviewed list of functions that compute over their arguments (`internal/parser/functions_allow.go`). `TABLESAMPLE`, `XMLTABLE`, `JSON_TABLE`, table names that contain path characters (`/ \ : * ? [`, DuckDB would open them as a file or URL), and qualified function names (`schema.f(x)` and the method form `x.f()`, which read a masked column unmasked) are rejected. Rejected requests return `ACL_REJECTED` and are audited as `reject`. The check runs in the query service before the rewrite cache, so it covers REST and MCP, and again in the rewriter. The table walker now also sees tables read inside `VALUES` lists and on the left side of `IN (subquery)`. **Behavior change:** a query that uses a function outside the list is rejected until the function is added. Write `f(x)` instead of `x.f()`. The unquoted keywords `user`, `current_user`, `session_user`, `current_role`, `current_catalog` and `current_schema` are rejected; quote a column that has such a name. A table whose name contains one of `/ \ : * ? [` can no longer be queried. An unquoted identifier that contains a non-letter Unicode character is now a parse error (`ERR_SYNTAX`), because DuckDB reads Unicode spaces as separators and pg_query does not; quote such identifiers.

- Stale example READMEs (mask providers "landing in v0.2" that are shipped, four MCP tools instead of nine).

### Removed

- **`ERR_FORBIDDEN` and `ERR_INSUFFICIENT_SCOPE`** — declared in the public error catalog but unreachable: no producer existed, policy denials use `ACL_DENIED`/`ACL_REJECTED`, and the approval endpoints deliberately answer uniform 404s. `ERR_INSUFFICIENT_SCOPE` returns with the OAuth work.

#### Query path

CTE-aware table walker, shape walker (`HasSelectStar`/`IsAggregate`/`HasCTE`/`HasUnion`/…), `StmtKind` whitelist, regex fallback. `FuzzParse` seeded.
- `internal/schema` — LRU cache (TTL 10 m, capacity 10 000), per-catalog singleflight, stale-serve on failure, `StaticLoader` for tests, Prom metrics (`sluice_schema_cache_{hits,misses}_total`, `_refresh_duration_seconds`, `_stale_entries`).
- `internal/datasource` — Registry with per-catalog `Status`, `AttachHook`, health ticker placeholder, `Probe` method. Six drivers: `sqlitefile`, `duckdbfile`, `postgres`, `mysql`, `s3parquet`, `motherduck`. Shared helpers under `drivers/common` (`ValidateIdentifier`, `EscapeSQLString`, `BuildCreateSecret`, S3 glob matching).

- `internal/executor` — hardened DuckDB pool (`external_access=false`, `allow_community_extensions=false`, `lock_configuration=true`), AttachHook-first init, `Request` → `Response{Columns, Rows, Truncated}`, `RowIterator` delegating `Scan` to `*sql.Rows`, per-request timeout + cancel.
- `internal/policy` — Engine with atomic snapshot swap; conflict resolver (deny-override → default-deny → row-filter combine → mask tiebreaker priority/specificity/name); templates `{{ subject.* }}` / `{{ request.* }}` render to `$N` params; CEL + QueryReject expressions declared-only. `FuzzTemplate` seeded.

### Security

- Every source file carries an SPDX header; `scripts/check-spdx.sh` enforces in CI.
- Default-deny: empty policy snapshot rejects every query (invariant covered by a test on every policy-touching slice).
- Templates never concatenate subject/request values into SQL — always flow through positional `$N` parameters.
- API-key failures add bounded random jitter so unknown-key-id vs bad-HMAC cannot be distinguished by response time.
- Admin port runs on its own listener and emits a loud warning if configured with an empty token.
